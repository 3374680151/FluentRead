# 精简版改造规划（2026-10-30）

> 场景收窄为：**个人写博客，需要翻译和纠错**。目标 8 个功能点、1 个页面。
> 本文回答两件事：GitHub 有没有现成的、现有代码怎么改。

---

## 一、结论

1. **不换项目。** 现有 FluentRead（8.1k star）有 40+ 翻译供应商适配层、划词卡 UI、ECDICT 词典，
   这些是资产。换项目等于把这些重写一遍。
2. **砍到 8 个功能点。** 详见第五节。
3. **两块借轮子**：**LiteLLM 做模型网关**（多模型 + 自定义模型 + 预算 + 用量，必选）、
   FluentRead 自己的组件做划词卡。纠错**不引入 LanguageTool**——它是 Java 服务，
   为一个语法检查跑 JVM 太重；只借鉴它的错误分类体系，用大模型实现。
4. **后台不做页面。** 模型与额度在 LiteLLM 配，用量看 LiteLLM 自带 UI。
   我们只做一个 `/api/config` 把可用模型下发给前端。

## 二、GitHub 现成项目对照

| 项目 | 是什么 | 能借什么 | 解决不了什么 |
| --- | --- | --- | --- |
| **FluentRead**（本项目，8.1k★） | 双语翻译扩展 | provider 适配层、划词卡、ECDICT 词典、术语库 | 本身就是扩展，不能免安装 |
| **kiss-translator**（fishjar） | 双语对照扩展 + 油猴脚本 | 双语渲染的排版思路、输入框翻译 | 仍是扩展形态 |
| **Read Frog**（mengxi-ream） | AI 翻译扩展 | 划词卡与朗读的交互细节 | 仍是扩展形态 |
| **openai-translator**（yetone） | 划词翻译 / 润色 / 总结 | **润色的 prompt 与"原文→建议"的展示方式**，正好对应纠错 | 桌面端 + 扩展，无网站 |
| **translate.js**（xhlhr / zvo） | 两行代码整页翻译 | "一行接入"的 SDK 形态与配置方式 | 只做整页替换，没有划词 |
| **LanguageTool** | 语法/拼写/标点规则引擎，Java，docker 8010，`/v2/check` | 只借它的**错误分类体系**（拼写/语法/标点/风格/冗长/大小写）当 prompt 骨架，**不部署** | 引擎本身过重，不为它跑 JVM |
| **LiteLLM** | 自建 LLM 网关，虚拟 key、预算、限流、用量 UI | **必选，当模型网关**：一个 OpenAI 兼容端点接住所有模型；加模型只改配置，不动业务代码 | 不管业务界面 |
| **LibreTranslate** | 自建翻译 API | 免费线路兜底 | 中英质量一般，不适合当主力 |

**判断**：界面层（写作台双栏 + 纠错列表）没有现成开源项目，必须自己写——但只有一个页面。
基础设施层（纠错引擎、模型网关）已经被开源做透了，自己写是浪费。

## 三、纠错怎么做（用大模型，不装 LanguageTool）

不引入 LanguageTool 的引擎，但把它的**分类体系**借过来当 prompt 骨架——
这样模型输出稳定、可分类、不会每次都换一套说法：

| 类别 | 查什么 | 例子 |
| --- | --- | --- |
| 拼写 | 拼错、同音词混淆 | `recieve` → `receive` |
| 语法 | 主谓一致、时态、冠词、介词 | `has been finished by me` → `I finished` |
| 标点 | 逗号粘连、大小写 | `However we` → `However, we` |
| 风格 | 被动滥用、冗长、重复 | `very important` → `critical` |
| 用词 | 不地道、搭配错误 | `do a mistake` → `make a mistake` |

**输出结构**（每条一条记录）：`原文片段 / 建议 / 类别 / 理由`。

**定位方式**：让模型逐字复制原文片段，前端用 `indexOf` 定位替换。
**不让模型返回字符偏移量**——它算不准，一旦偏一位就替换错地方。

**成本控制**：
- 只在你点"检查"时跑，不自动跑。
- 只检查目标语言段落，中文段落跳过（避免中英混排误报）。
- 按段落并行，单段失败不影响其他段。

**不做整段重写**——那会覆盖你的个人风格，你也无法逐条判断改了什么。

**界面**：问题列表，每条可「接受 / 忽略」，接受即替换原文对应片段。

| `web/public/fluentread-sdk.js` | 改 | 去掉词书依赖（词表改本地），只留划词/点词/悬浮球 |
| `web/public/index.html` | 改成 | 变成 `write.html` 的入口，或直接重定向 |
| `web/public/study.html` | **删** | 能力并入写作台 |
| `web/public/services.html` | **删** | 配置进环境变量 |
| `web/public/learn.html` | **简化** | 砍掉复习调度与统计，只留「词表」：列表 + 搜索 + 复制 + 导出 |

**不新建后台页面。** 站长要改模型或额度，改 `.env` 重启，或在 LiteLLM 的 UI 里点。

## 五、8 个功能点（验收就按这个）

| # | 功能 | 通过标准 |
| --- | --- | --- |
| 1 | 分段翻译 中→英 | `Ctrl+Enter` 后逐段出译文，单段失败不影响其他段 |
| 2 | 选中查词/短语 | 气泡 400ms 内出现，不遮住选区 |
| 3 | 英文纠错 | 问题列表逐条给「片段→建议→理由」，可接受 |
| 4 | 译文可改 | 改完即最终稿，重译时提示是否覆盖 |
| 5 | 固定译名 | 一行一条 `源词 = 译名`，翻译时自动套用 |
| 6 | 词表 | 收藏带原句，可搜索、复制、导出。**不做复习** |
| 7 | 复制 / 导出 Markdown | 双语并排或仅译文 |
| 8 | 划词气泡（SDK） | 你博客读者可用，一行 script |

## 六、三步走

| 步 | 做什么 | 完成标志 |
| --- | --- | --- |
| **D1 打通** | compose 起 web + litellm + db；`/api/config`、`/api/translate`、`/api/proofread` 三条通 | curl 三个接口都返回真实结果，模型清单来自 LiteLLM |
| **D2 写作台** | 双栏 + 分段翻译 + 纠错列表 + 固定译名 | 能把一篇中文博客翻成英文并纠错 |
| **D3 嵌入** | SDK 去词书依赖；部署到你的服务器 | 博客页面加一行 script 能划词 |

D1 不做完，D2 就是本地玩具。

## 七、风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 大模型纠错误报 | 改对的被标错，或漏报 | 每条必须给理由，可疑条目可忽略；中文段落跳过；不自动替换，必须手动接受 |
| 多一层 LiteLLM | 每次请求多 20–50ms | 可接受；翻译本来就慢 |
| 免费线路对公网流量不稳 | 访客偶发失败 | 失败自动换线 + 明确提示，不静默重试 |
| 只支持 txt/md 之外的格式 | 想翻 PDF 时不行 | 明确不做，需要时用 PDFMathTranslate 单独跑 |

## 八、一句话

**8 个功能点、1 个页面、3 个容器。** 现有代码留下 provider 层和划词卡，删掉 4 个页面，
新增 1 个页面。这比从零开始快，也比实现 28 个模块靠谱。
