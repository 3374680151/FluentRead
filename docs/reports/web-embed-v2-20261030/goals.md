# 目标（一页纸）

> ⚠️ **方向已更正（2026-10-31）**：本文"左中文右英文"的表述是错的。
> 真实需求是**左边写英文、右边看中文回译**（作者用英文写作，中文用于回译校验），
> 纠错是核心功能而非附属。以 `FluentRead-Go/docs/10-requirements.md` 为准。
> 本文其余判断（零配置、单页面、两容器、判断标准）仍然有效。

> 这份文档只回答"我要做成什么"，不回答"怎么做"。设计见 `slim-plan.md`。

---

## 一句话

**在自己博客上写中英文文章时，能随手翻译和纠错；读者打开博客就自带划词翻译，不用装任何东西。**

---

## 两个使用者，两个目标

### 我：写的人

| 我要什么 | 为什么 |
| --- | --- |
| 写中文，出英文 | 博客要中英双语，但我英文写作慢 |
| 术语全篇一致 | 同一个概念不能一会儿一个译法，读者会困惑 |
| 写完能纠错 | 我英文的语法和搭配不稳，需要逐条指出来 |
| 不确定就查，不离开编辑区 | 切窗口查词会打断思路 |
| 逐段改，不要整段重写 | 整段重写会覆盖我的语气，我也没法判断改了什么 |

### 我的读者：读的人

| 我要什么 | 为什么 |
| --- | --- |
| 选中生词就能看释义 | 读者不一定会英文 |
| 不用装插件、不用注册、不用填 key | 让读者为读我一篇文章装东西，不现实 |
| 看到好词能存下来 | 顺手，不是必需 |

## 做到什么算成功（可验证）

| # | 标准 | 怎么验 |
| --- | --- | --- |
| 1 | 一篇 800 字中文博客，30 分钟内翻成英文并改完 | 真写一篇，计时 |
| 2 | 读者首次访问到看到第一个译文 ≤ 3 秒，**0 次配置** | 清空浏览器打开，计时并录屏 |
| 3 | 纠错建议里我认可的占多数（≥70%） | 抽 50 条人工判断 |
| 4 | 全站不存在"请填写 API Key"这类界面 | 全局搜 UI 文案 |
| 5 | 模型成本可预估且能封顶 | 看账单，不超过设定值 |

第 2 条和第 4 条是硬门槛：只要有一条不过，这次改造就算失败。

---

## 不是什么（边界）

| 不是 | 原因 |
| --- | --- |
| 学习产品 | 不做复习调度、背单词、学习统计。收藏留一个列表就够 |
| 文档处理工具 | 不做 PDF / DOCX 导入。要翻 PDF 另有工具 |
| 多引擎评测平台 | 不做多服务横向对比。选一个能用的就行 |
| 通用 SaaS | 只服务我的博客和我自己，不做多租户 |
| 管理后台 | 配置走环境变量，不做配置页面 |

**判断标准**：一个新功能如果不能让"30 分钟写完一篇双语博客"更快，就不做。

---

## 约束

- 部署在**自己的服务器**，一个人维护，不能有需要天天盯的组件。
- **不为一句语法检查跑一个 JVM**，所以不部署 LanguageTool。
- **能少一个容器就少一个**，所以不跑 LanguageTool；但**模型网关必须留**——
  "支持各种模型 + 自定义模型"这件事，自己写适配器的代价远高于多一个容器。
- **访客零配置是硬底线**，任何需要读者先填东西的方案直接否掉。

## 最终形态

```
1 个页面   写作台（左中文右英文 + 纠错列表 + 词表）
1 个 SDK   博客划词（一行 script）
2 个容器   web 服务 + 模型网关（LiteLLM）
N 个 key   接几家模型就配几个，随时加减
```

**模型这件事的边界**：加一家新模型 = 在网关配置里加一条，**不改业务代码**。
这是当初砍掉 40 家 provider 适配器的理由，也是留下网关的理由。

---

## 还没定的三件事

1. **词表存哪**：只存本机（简单，换设备丢）／存服务端（要加数据库和访客 id）。
2. **用哪家模型**：决定成本和纠错质量，DeepSeek / 通义 / GPT 都行，看你能拿到什么。
3. **域名**：SDK 要挂在哪，决定嵌入代码长什么样。

这三条定了就能开工，不定也能先用本地默认值跑起来。
